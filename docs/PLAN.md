# 核心玩法完成目标计划

> 本计划根据当前代码完成度评估表编写。
> 目标不是扩展游戏外围内容，而是把已经存在的核心玩法从“可玩 Demo”收口为“稳定、完整、可验证的核心玩法版本”。

## 二、本计划的总目标

### 总目标：完成当前核心玩法垂直切片

在不新增外围系统的前提下，把当前已有的“一关、20 波、四把武器、六类敌人、五个 Boss、八属性、二十三种反应、66 张卡牌”做成一个稳定闭环。

完成后，玩家应当能够：

1. 从主菜单选择任意一把武器并正常开始游戏。
2. 经历完整的白天远征、夜晚防守、波次推进和升级选卡。
3. 使用四把武器的不同普通攻击、主动技能和专属卡牌路线。
4. 在战斗中稳定触发属性状态、属性反应和攻击增强模组。
5. 遇到五个 Boss 的不同技能和狂暴阶段。
6. 通过灵核被摧毁、玩家死亡、最终 Boss 被击败或终局时间结束完成唯一一次结算。
7. 在结算时知道本局使用了什么武器、获得了哪些卡牌、触发了哪些关键机制以及最终如何结束。

本计划完成后的目标状态是：

| 目标 | 期望结果 |
|---|---|
| 核心玩法循环 | 从开局到结算无状态断裂、卡死、重复结算或重开污染 |
| 战斗系统 | 已有攻击、属性、状态和 Boss 模组全部可重复验证 |
| 内容数量 | 现有内容全部能在正确的波次、武器或前置条件下被访问 |
| 武器系统 | 四把武器的实际运行行为、主动技能、起始属性和专属卡牌一致 |
| 构筑系统 | 卡牌池、等级、前置、武器限制和构筑展示准确可靠 |
| 整体核心版本 | 成为可持续开发和回归验证的核心玩法基线 |

## 三、维度目标

### 目标一：核心玩法循环达到可完整通关

### 当前问题

- 20 波流程已经存在，但需要进一步验证所有昼夜切换、波间事件、Boss 生成和结算路径。
- 玩家死亡、灵核摧毁、最终 Boss 击败和终局计时结束存在多个结束入口，需要确保它们不会重复触发。
- 重开或返回菜单后，需要确认上一局的敌人、Boss、卡牌、属性和计时状态全部清理。

### 目标内容

- 固化白天开始、白天结束、夜晚开始、夜晚结束和波间选择的状态转换。
- 验证每一波只能开始一次、结束一次，不能跳波或重复推进。
- 验证灵核生命、灵核护盾、玩家生命和游戏结束状态之间的关系。
- 验证暂停期间刷怪、伤害、技能冷却、危险区域和计时都正确冻结。
- 验证胜利和失败只发出一次，并且结算后停止所有战斗行为。
- 验证开新局时 GameManager、WaveManager、UpgradeManager 和场景实体不会残留上一局状态。

### 交付物

- 20 波流程状态检查表。
- 四种失败/胜利路径的自动化测试。
- 重开、返回菜单、再次开始的生命周期测试。
- 波次状态和结算状态的必要代码修正。

### 完成标准

- 任意一把武器都可以从第 1 波走到终局。
- 20 波流程没有卡死、跳波、重复 Boss、重复结算或无法重新开始的问题。
- 游戏结束后不会继续刷怪、掉经验、造成伤害、触发升级或执行主动技能。

### 目标二：战斗系统达到规则闭环

### 当前问题

- 基础攻击和高级攻击模组已经较多，但需要验证它们叠加时的执行顺序和边界。
- Boss 配置中的技能冷却字段目前没有完整传递到运行时，部分 Boss 会回退到默认冷却。
- 灼烧、中毒、减速、冻结和眩晕等状态已有部分数值/物理效果，但怪物身上没有状态图标、层数、剩余时间或专属状态特效。
- 属性反应目前主要通过 HUD 顶部的全局文字 Toast 反馈，玩家无法直接判断具体是哪只怪物处于什么状态。
- 冰属性本身目前主要负责减速，真正的冻结主要由属性反应触发；藤属性“叠满后束缚”的描述与实际行为还没有完全一致。
- 无头场景测试可以验证启动，但当前截图测试不能直接证明真实画面验收成功。

### 目标内容

- 修正 Boss 技能冷却配置接线，让五个 Boss 使用各自的配置值。
- 验证 Boss 普通状态、半血狂暴状态、技能预警、蓄力、释放和冷却流程。
- 验证近战命中框、远程弹道、穿透、返回弹道、命中冷却和击退。
- 验证暴击、裂痕、过杀、护盾反击、死亡爆炸和连续击杀之间的组合顺序。
- 验证灼烧、中毒、冻结、减速、眩晕、扩散、连锁和碎裂在目标死亡时的处理。
- 补齐怪物负面状态的目标表现：状态图标/颜色、层数、剩余时间和状态切换反馈。
- 为灼烧、中毒、冰霜/冻结、藤蔓减速、雷属性眩晕等状态提供轻量、可读的怪物身上特效；这些属于战斗可读性，不属于大规模视觉升级。
- 让状态表现与 `AttributeStatusComponent.statuses`、`frozen_time` 和 `stunned_time` 同步，状态结束、目标死亡或 Boss 销毁时立即清理。
- 修正文档与运行规则不一致的状态描述，明确“冰属性减速”和“属性反应冻结”的区别。
- 验证危险区域、投射物和持续状态在 Boss 死亡或游戏结束后正确销毁。
- 将逻辑测试、场景启动测试和真实渲染验收分开，避免测试结果产生误解。

### 怪物负面状态表现目标

| 状态 | 当前物理效果 | 本计划补齐的目标表现 |
|---|---|---|
| 灼烧 | 持续伤害 | 火焰/红橙色受击反馈、状态图标、层数和剩余时间 |
| 中毒 | 持续伤害、降低治疗 | 绿色毒雾或毒色轮廓、状态图标、层数和剩余时间 |
| 冰霜减速 | 降低移动速度 | 蓝色冰霜轮廓或脚下冰环、状态图标和剩余时间 |
| 冻结 | 暂停移动和行动 | 冻结覆盖、冰环/冰块反馈、冻结剩余时间 |
| 藤蔓减速 | 降低移动速度 | 藤蔓缠绕或绿色束缚标识 |
| 眩晕/僵直 | 暂停移动和行动 | 头顶眩晕/雷电标识和剩余时间 |

爆、水和部分风属性主要作为反应前置或扩散条件，不需要在本阶段强行增加独立的负面状态特效；但它们的层数和持续时间必须能够在调试或目标状态面板中被验证。

### 交付物

- 五个 Boss 的运行时配置和技能行为测试。
- 基础伤害链和攻击模组边界测试。
- 属性状态与目标死亡处理测试。
- 怪物负面状态展示节点或等价表现层。
- 状态图标、层数、剩余时间和状态结束清理测试。
- 独立的逻辑 Smoke Test 和场景 Smoke Test。
- Boss 技能冷却字段接线修正。

### 完成标准

- 五个 Boss 的实际数值和技能行为与配置一致。
- 每个主要攻击模组至少有一个可重复的自动化验证。
- 灼烧、中毒、减速、冻结和眩晕等状态的物理效果与目标表现一致。
- 玩家可以从怪物身上识别当前状态、层数和剩余时间；状态结束后表现立即消失。
- 目标死亡、攻击源销毁、Boss 销毁和游戏结束不会产生重复伤害或空引用。
- 测试能够明确区分“场景启动成功”和“真实画面已经验收”。

> 本目标只验证规则正确性，不在本阶段做全局难度曲线和数值平衡调整。

### 目标三：现有内容数量全部可访问、可验证

### 当前内容清单

| 内容类型 | 当前数量 | 目标 |

### 目标内容

- 检查六类敌人是否都能在实际波次中出现，并使用自己的行为逻辑。

- 将“代码中定义了但实际运行不可访问”的内容标记出来并处理。

### 交付物

- 波次—敌人—Boss 出现关系表。
- 属性—反应—效果覆盖表。
- 卡牌定义—前置—运行时效果覆盖表。
- 缺失接线或不可达内容的修正清单。

### 完成标准

- 当前已声明的核心内容没有关键的“只定义未接入”项目。
- 所有敌人、Boss、属性反应和卡牌至少有一条可执行访问路径。
- 不增加内容数量，但现有内容不能因为入口、前置或运行时分支问题被隐藏。

### 目标四：武器系统达到四把武器可独立成立

### 当前状态

- 四把武器在 Player 实际运行分支中已经有不同伤害、攻击方式和主动技能。
- `WeaponRuntime` 已开始承接四把武器的数值、属性、视觉资源、主动技能和局内状态描述。
- 旧的 WeaponBase/MeleeWeapon/RangedWeapon 体系正在移除；完成后不再存在与 Player 重复的武器数据来源。

### 目标内容

为四把武器各自建立一条可验证的运行契约：

| 武器 | 起始属性 | 普通攻击 | 主动技能 | 专属卡牌 |
|---|---|---|---|---|
| 引霜灵剑 | 火 | 近战横斩、剑气横扫、火焰轨迹 | 赤焰回环 | 回风斩、焚痕 |
| 破鳞钢刃 | 毒 | 快速连斩、连击、毒云 | 腐心散 | 连刃、毒爆 |
| 龙脊长枪 | 冰 | 长距离突刺、蓄力、穿透 | 霜锋震 | 贯阵、碎冰 |
| 火符连铳 | 雷 | 自动弹道、蓄能、穿透 | 天雷引 | 定装雷符、守线 |

需要完成：

- 确认四把武器实际运行时的基础伤害、攻击间隔、范围和目标选择规则。
- 确认主动技能的冷却、伤害、属性、范围、目标数量和特殊效果。
- 验证四把武器切换后不会残留上一把武器的参数、属性或特殊状态。
- 验证武器专属卡只对正确武器开放，获得后确实改变对应攻击行为。
- 将 `WeaponRuntime` 明确为生产战斗、主菜单和 HUD 共用的权威数据源。
- 删除过期的武器继承脚本、独立武器场景和空入口，避免后续误改无效代码。

### 交付物

- 四把武器运行契约表。
- 四把武器的普通攻击、主动技能、起始属性和专属卡回归测试。
- 武器选择、重新开始和切换状态清理测试。
- 独立武器脚本与实际运行分支的边界说明。

### 完成标准

- 四把武器都能独立完成一局核心流程。
- 每把武器都能证明“起始属性 → 普通攻击 → 主动技能 → 专属卡牌”链路有效。
- 任何武器都不会错误读取其他武器的属性、攻击参数或构筑 Modifier。

### 目标五：构筑系统达到可解释、可验证

### 当前基线

- 卡牌定义：66 张。
- 卡牌最大等级槽位：99 个。
- 单个武器理论可用卡牌定义：60 张。
- 属性卡：8 张。
- 武器专属卡：8 张。
- 有前置条件的卡牌：12 张。
- 主要构筑方向：单属性过载、多属性反应、暴击爆炸、过杀连锁、护盾反击、残影、裂痕收割、返回弹道、击杀节奏、移动蓄势、灵核守护、日夜取舍、彩虹属性和主动技能等。

代码没有固定的 `Build` 类，也没有预设固定 Build 数量；这是有意的设计。Build 就是玩家在本局已经选择的卡牌和由此形成的攻击路线，HUD 只负责展示当前构筑，不负责管理、保存或规划构筑。

### 目标内容

- 验证卡牌最大等级、当前等级和下一等级效果一致。
- 验证卡牌前置条件、武器限制和已获得状态一致。
- 验证三选一不会出现重复卡、满级卡、错误武器卡或不可满足前置的卡。
- 验证卡牌效果实际进入 `base_stats`、属性精通或 Modifier 运行链。
- 验证同一张卡重复升级不会重复注册信号、重复叠加一次性效果或覆盖错误状态。
- 验证卡牌不足以组成完整路线时，仍有稳定的候选兜底规则。
- 在 HUD 中清楚展示已获得卡牌、当前等级和关键行为效果。
- 提供轻量本局构筑视图，方便玩家确认当前实际形成的路线；不新增持久化记录或 Build 管理。

### 交付物

- 66 张卡牌的定义统计和可获得性检查。
- 卡牌前置链和武器限制测试。
- 卡牌效果到运行时 Modifier 的映射表。
- 三选一候选生成测试。
- 局内构筑视图和构筑状态回归测试。

### 完成标准

- 卡牌池没有明显无效、不可达或获得后无效果的卡牌。
- 卡牌等级、描述、实际效果和 HUD 状态一致。
- 四把武器的专属卡不会串到其他武器。
- 至少能稳定验证前述主要构筑方向，而不是只在代码中存在零散 Hook。

> 本目标不增加装备掉落、商店、货币或局外成长，也不承诺每局都能凑齐某一套构筑。
